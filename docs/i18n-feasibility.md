# 国际化（i18n）可行性评估

> 状态：**已评估，未实施**（2026-08）。本文档记录对本项目引入国际化的可行性评估、改造方案与风险点，包括英文支持与「GitHub PR 自助提交语言包」两条主线。

## 结论

**核心英文化 + en-US 语言包 + GitHub PR 提交流程：中等偏低~中等难度，约 5~9 个工作日**（按熟悉本仓库的开发者估算）。

「自助提交语言包」已确定为 **GitHub PR 方式**，不做 App 内提交：

- **审核 = 代码评审**：无需建审核后台、语言包状态表、垃圾提交治理。
- **PWA 离线冲突被天然化解**：语言包在构建期用 `import.meta.glob` 打进 bundle，随 Service Worker 预缓存自动生效，零运行时拉取；代价只是新语言随下一个版本发布，可接受。

难度不在「引入 i18n 库」，而在文案规模、服务端错误消息与 e2e 测试三块隐藏成本。

## 现状盘点

- **没有任何 i18n 基础设施**：无 vue-i18n、无 locale 状态，`index.html` 为 `lang="zh-CN"`，所有文案硬编码在组件里。
- **文案规模**：约 30 个文件、470+ 处中文行（含代码注释与数据内容），实际需提取的 UI 字符串约 **350~450 条**。大头集中在 ImportPage（73）、RoomSettingsPage（61）、HomePage（44）、RoomDetailPage（41）。
- **第三方库全部有官方 locale 支持**：Vant 4（`Locale.use`）、dayjs、ECharts、AG-Grid（`localeText`），这部分成本很低。
- **README_en.md 已存在**，可作英文术语与翻译风格基准，减少翻译决策成本。
- **e2e 测试全部断言中文文案**：9 个 spec 文件约 570 处中文文本断言。
- **服务端错误消息是中文**：数据库 RPC 会 `raise exception '该成员已在账单分摊中…'`，前端约 15 处直接 `showToast(e.message)`。

## 改造方案

### 1. 核心英文化（含 en-US 语言包）

- 接入 vue-i18n，提取全部 UI 字符串（含动态拼接如「解析失败：」+ message、模板插值、复数/性别）。
- 语言切换入口 + localStorage 持久化，完全复用 `useTheme` 的模式。
- Vant / dayjs / ECharts / AG-Grid 四件套 locale 同步，切换时重渲染。
- 全量 en-US 翻译，以 README_en.md 为风格基准。

### 2. GitHub PR 自助提交语言包

- 语言包目录 `src/locales/*.json`，key 与基准语言包完全对齐。
- **校验脚本**（提交流程的灵魂）：JSON 合法性、key 对齐（缺失/多余）、占位符 `{x}` 一致性、单条长度上限、语言代码查重；保证社区提交的语言包永远不缺 key，缺失 key 回退中文。
- **GitHub Actions**：仅对 `src/locales/**` 变更触发校验。注意：仓库当前**没有任何 CI**（无 `.github` 目录），属净新增基础设施（workflow 文件 + pnpm setup）。
- 语言设置 UI 构建期枚举语言列表；`index.html` lang 与 PWA manifest 需随语言处理（manifest 是静态的，只能做有限处理）。
- 贡献者文档（翻译指南，建议中英双语，引用 README_en.md 作为术语基准）。

### 3. 配套改造（容易漏的部分）

- **服务端错误本地化**：把 RPC 中文异常改为错误码，前端做 message → 本地化映射（约 15 处 `e.message` 直接展示）。
- **日期/金额本地化**：`src/utils/format.ts` 目前是中文日期格式，需按 locale 切换；ImportPage 日期解析保持对中文年月日字符的宽容。
- **长内容双语**：隐私协议（PrivacyDialog）、更新日志正文（markdown 数据内容）不是简单 key 替换，需要双语存储或按 locale 切数据源。
- **边界划分**：房间名、成员名、账单内容是用户数据，绝不翻译；「本地/在线/过期」等房间状态徽章是 UI 状态标签，需要翻译。

## 工作量估计

| 工作项 | 说明 | 估计 |
| --- | --- | --- |
| 核心 i18n 改造 | vue-i18n + 约 400 条文案提取 + 语言切换与持久化 | 3~5 天 |
| en-US 语言包 | 全量翻译（有 README_en 参考） | 1~2 天 |
| GitHub PR 提交流程 | 校验脚本 + Actions workflow（净新增）+ 构建期打包 + 贡献者文档 | 1~2 天 |
| 服务端错误本地化 | 错误码映射 + 前端本地化 | 0.5~1 天 |
| **合计** | | **约 5~9 个工作日** |

## 主要风险点

1. **服务端中文错误消息**：最容易漏的隐藏工作，英文用户会直接看到中文报错。
2. **e2e 的 570 处中文断言**：只要保持**默认语言为中文、英文为可选项**，测试完全不用动；若默认语言改英文则需大量改选择器。建议默认中文。
3. **长内容双语策略**：隐私协议与更新日志正文需要数据层方案，不是纯 key 替换。
4. **日期/金额本地化**：format.ts 与 ImportPage 解析逻辑需要 locale 感知。
5. **用户数据边界**：房间/成员/账单内容不翻译，状态标签要翻译，容易混淆。

## 落地顺序建议

先做核心英文化 + en-US（GitHub PR 流程可同步搭建），验证收益后再决定是否扩展语言。整体是「量大但不高难」：无算法或架构难题，主要是文案机械提取 + 一条干净的 CI 校验链路 + 服务端错误本地化收尾。
